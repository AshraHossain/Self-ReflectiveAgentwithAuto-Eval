<objective>
Build the workflow registry: the entrypoint allowlist, the `Workflow` schema, and the capability gate that refuses a registration whose policy demands something the target backend cannot provide.

Purpose: this is the implementation of the project's founding architectural decision — that uniform durable pause/resume across LangGraph, CrewAI and ag2 is impossible, and the honest resolution is a declared capability matrix that fails loudly at registration rather than faking parity (STATE.md §Decisions, init). WORKFLOW-03 is that failure. It is also the module where a caller-supplied string gets closest to a code path, which is why it contains no import machinery at all and why that is asserted from the syntax tree rather than from a text search.

Output: `src/eacp/registry.py`, `CAPABILITIES` on the three adapter placeholders, `tests/test_registry.py`.

Scope boundary: the registry is process-local for v1 (D-13) — registration happens in Python at startup, nothing is persisted. The `runs` table that plan 02-02 built is deliberately self-contained, carrying `workflow_id`, `backend_type`, `policy_id` and `policy_hash` as columns rather than as foreign keys, so Phase 4's second-process approval CLI reads run history without ever needing this registry. Flagged for the Phase 4 planner.

Source coverage audit for the whole phase: see `02-01-PLAN.md` `<source_audit>`.

    **The entrypoint is an allowlist key, not a path.** The application author calls
    `register_entrypoint("contract_review", build_graph)` in Python; the workflow's `entrypoint` field
    carries only that dict key. D-10 locks this, and WORKFLOW-01 forces it: a dotted import path would
    make the pointer *transparent* — it would encode module structure — and resolving it would mean
    handing a caller-supplied string to import machinery, which is the exact pattern Phase 1's
    `backends.py` allowlist exists to prevent.

    - `_NAME_RE` — a conservative lowercase charset, 64 characters max, first character alphanumeric.
      These names surface in error messages, in run records, and in Phase 4's CLI output, so a
      constrained charset means they are never a log-injection or path-traversal shaped string.
    - `_ENTRYPOINTS` — a module-level name-to-callable dict.
    - `register_entrypoint(name, fn)` — checks the charset first, then refuses a name that is already
      registered with `DuplicateEntrypointError`. Silently swapping what a registered name executes is
      a hijack primitive in any process that imports third-party workflow modules (T-02-05).
    - `resolve_entrypoint(name)` — a dict lookup only, raising `ValueError` listing the registered
      names, chained from `None` exactly as `load_backend_module` does.

    **This module must contain no import machinery of any kind** — no dynamic import call, no
    `__import__`, no `exec`, `eval` or `compile`. Import stays in `backends.py`, which is the package's
    single chokepoint and already has the allowlist-before-resolution guard Phase 1 verified. Write
    `test_registry_has_no_import_machinery` to parse this module's source into a syntax tree and assert
    that none of those names appears as an imported module, a referenced name, or an attribute access.
    Parsing rather than grepping is deliberate and is the correction of a real Phase 1 defect: a text
    search over this file would also match the explanatory comment describing the rule, which makes
    the gate fire on correct code and pushes the next person to delete the comment or waive the gate.

    **The `Workflow` schema.** A pydantic model with `extra="forbid"` and exactly the six WORKFLOW-01
    fields: `id`, `name`, `description`, `backend_type`, `entrypoint`, `policy_id`. All required, no
    defaults. `backend_type` is a `Literal` over the three backend names — keep the Literal rather than
    a runtime check against `available_backends()`, because the Literal is what gives mypy narrowing
    at every adapter call site; the drift test is what keeps it honest. Constrain `id` and `entrypoint`
    with the same `_NAME_RE` used by `register_entrypoint`, so one regex governs every name the
    registry can emit.

    `extra="forbid"` is what makes `nodes`, `agents` and `edges` rejections rather than ignored keys —
    WORKFLOW-01 is explicit that workflow *topology* has no place in this schema. Say so in the class
    docstring, because the pull toward adding a `nodes` field is strong and the reason it is refused is
    not self-evident from the field list.

    No YAML loading here. Nothing in Phase 2 loads a workflow from a file — `register_workflow` takes
    objects — and `load_yaml_mapping` in `policy.py` is already the package's single hardened YAML

    1. The workflow's entrypoint is in the allowlist. A pure dict lookup, no filesystem, no import.
    2. The workflow's `backend_type` is a known backend name. A pure dict lookup.
    3. Only now, `load_backend_module(backend_type)` and the capability comparison.

    Step 3 is the only one that touches the filesystem and the only one that can raise about
    installation. Running it earlier means a workflow with a *misspelled entrypoint* reports "install
    `eacp[crewai]`" — an error about the wrong thing entirely, sending the author to fix an
    environment that was never broken. This ordering also makes the common failure the cheapest check.

    **The gate itself** is a set difference: the capabilities the policy requires, minus those the
    backend module declares. If anything remains, raise `CapabilityError` naming the workflow, the
    missing capabilities, the backend, and what that backend does provide. Also compare in the other
    direction: if the adapter declares a name outside `KNOWN_CAPABILITIES`, raise. mypy catches a typo
    in an adapter statically, but only when that adapter's framework is installed — otherwise it is
    skipped under the missing-imports override — so this one runtime line is what actually closes it.

    Reach the adapter only through `load_backend_module`. That is the package's single lazy-import
    chokepoint, it already runs its allowlist lookup before any import, and it already translates a
    missing framework into an install hint. Using it is what keeps this module free of import
    machinery while still reading a constant that lives inside an adapter.

    **`_WORKFLOWS`** is a plain module-level dict, process-local, not persisted (D-13). Refuse a
    second registration under an existing id for the same reason `register_entrypoint` does. State in
    the module docstring that the registry is deliberately not persisted and that the `runs` table is
    self-contained so Phase 4's cross-process CLI never needs it — otherwise Phase 4 discovers the
    question cold.

    Record the honesty gap as a short note in `register_workflow`'s docstring: nothing in Phase 2
    verifies that a backend declaring durable approval actually delivers it. That belongs in
    CONFORM-01's parametrized suite, written as "for each adapter, durable approval is declared if and
    only if a run survives a process exit". Writing it down here is what carries it to Phase 7 instead
    of losing it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caller-supplied `entrypoint` string → code resolution | The closest a string gets to executable code anywhere in this phase. A workflow definition may be authored by someone other than the operator. |
| Third-party workflow module → `register_entrypoint` | Any imported package can call into the allowlist at import time. Whether it can *displace* an existing registration is the whole question. |
| Adapter module `CAPABILITIES` → the registration gate | A declared constant is trusted as a statement about runtime behaviour. Nothing in this phase can verify the claim. |
| `register_workflow(workflow, policy)` argument pair | Two objects that name each other. If they disagree, every run record downstream pins the wrong policy hash. |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04 | Elevation of Privilege | `registry.py` entrypoint resolution | high | mitigate | A caller-supplied entrypoint string reaching an import target would be arbitrary code execution from a config file.
