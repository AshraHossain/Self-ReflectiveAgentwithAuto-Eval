<objective>
Build the run-history layer: the synchronous `RunStore` Protocol that Phases 5, 6 and 7 type against, and the SQLite implementation that backs it for v1. Plus the two `pyproject.toml` configuration gates the rest of the phase depends on.

Purpose: TRACE-03 asks for a *pluggable* store with a SQLite implementation. Pluggability here is structural typing, not inheritance — a third-party store must not have to import `eacp` internals. 02-RESEARCH.md §Finding 7 measured that the runtime conformance decorator would pass a class whose every method has the wrong arity, so the conformance check is static and the type-check configuration has to actually work before that check means anything. This plan also creates the project's first persistent on-disk artifact, which is why file permissions and the deprecated-datetime trap are in scope here rather than deferred.

Output: `pyproject.toml` (two config blocks), `src/eacp/store.py`, `tests/test_store.py`.

Scope boundary: approval records and audit-log records are Phase 4 and get their own Protocols — 02-RESEARCH.md §Anti-patterns is explicit that they do not belong in `RunStore`. OpenTelemetry attribute naming is Phase 5 (TRACE-02); the `attributes` column is a free-form JSON blob precisely so Phase 5 needs no migration and Phase 2 imports no OTel.

    Create `src/eacp/store.py`. Build it from 02-RESEARCH.md §Finding 6 and §Code Example 4, both
    executed in this repo's venv with their outputs recorded. This task delivers the types, the
    schema, and the three write methods; Task 3 delivers the reads and the security gates.

    Imports: stdlib only plus `typing`. No agent framework at any scope. Nothing from `eacp.policy`
    or `eacp.registry` — the store is independent of both, which is what lets this plan run in the
    same wave as 02-01.

    **The records.** `RunRecord` and `StepRecord` are frozen, slotted dataclasses, not pydantic
    models: they are produced by our own adapter code rather than parsed from untrusted input, so
    validating on every step write buys nothing and costs allocation on the hot path (one append per
    node). `RunRecord` carries `run_id`, `workflow_id`, `backend_type`, `policy_id`, `policy_hash`,
    `status`, `started_at`, `ended_at` and `metrics`. `StepRecord` carries `run_id`, `seq`, `name`,
    `started_at`, `ended_at`, `outcome` and `attributes`.

    `RunStatus` is a `Literal` over the states a run can actually be in: running, awaiting approval,
    succeeded, failed, denied. The last two exist because APPROVAL-03 makes a denied approval a halt
    and BUDGET-01 makes a budget block a halt, and those are different outcomes from a crash.

    **Timestamps are ISO-8601 UTC strings, stored as TEXT.** Never a datetime object handed to the
    driver — Python 3.12 deprecated the implicit adapter and Task 1's warning filter now makes that a
    test failure. Never a naive datetime and never an epoch float. Provide a small module-level helper
    that produces the canonical form with microsecond precision, and use it everywhere. The string
    form is independently what you want: ISO-8601 UTC sorts lexicographically, which is exactly what
    Task 3's ordering and `since` filter rely on.

    **`run_id` is generated by the caller, not the store.** Three downstream requirements force it:
    LANGGRAPH-02 pins the checkpointer's `thread_id` to the run_id, so it must exist before the graph
    is compiled and therefore before the store is touched; CREWAI-03 starts run-identity propagation
    at the adapter; and a store outage should fail the history write, not block the run from starting.
    Document `uuid.uuid4().hex` as the expected shape in the Protocol docstring. Not the newer
    time-ordered UUID variant — it is absent on 3.12 and `requires-python = ">=3.11,<3.14"` excludes
    the version that adds it. Sortability comes from the `started_at` column and its index.

    **The Protocol.** `RunStore` is a plain `typing.Protocol` with six synchronous methods —
    `start_run`, `finish_run`, `append_step`, `get_run`, `list_steps`, `list_runs` — with the exact
    signatures in §Finding 6. Synchronous is D-06, locked: SQLite's stdlib driver is synchronous, so
    this matches the real I/O; the one async caller (ag2 middleware) bridges with a thread offload in
    its own adapter, which is one line per call site inside `ag2_adapter.py`.

    Do **not** decorate the Protocol to make it checkable at runtime. 02-RESEARCH.md §Finding 7
    executed both halves: the runtime check returned True for a class whose every method had the wrong
    arity and return type, while `mypy --strict` caught that same class precisely on a one-line
    annotated assignment. A check that passes the exact failure a pluggable interface exists to
    prevent, while looking to a reviewer like it was verified, is worse than no check. The static
    probe in `tests/test_store.py` is the real conformance gate, and Task 1 is what makes it able to
    report green.

    **`SQLiteRunStore.__init__`** takes a path, creates the parent directory if it is missing (the
    driver fails with an unhelpful "unable to open database file" otherwise), and bootstraps:
    set WAL journal mode as the very first statement after connecting and before any DML — with the
    legacy transaction default, the first DML opens an implicit transaction and the pragma then fails
    with "cannot change into wal mode from within a transaction" — then create the two tables and the
    `(workflow_id, started_at)` index, then set `user_version` to 1. WAL persists in the database file
    header, so it belongs here and not in the per-call connect. Migrations are a `user_version`
    comparison and an if-ladder when the schema next changes; no migration framework enters this
    project for two tables.

    **`_connect`** opens a fresh connection per call with a timeout, switches foreign keys on, and
    sets a row factory. Foreign keys default to off and the setting is per-connection — it does not
    persist in the file the way the journal mode does — so this is the one place it can be set. Put
    the measured tradeoff in a comment at this method: ~1.2 ms per write against 161 µs for a
    long-lived handle, roughly a millisecond per run-history row against LLM calls measured in
    seconds, in exchange for deleting thread affinity, connection lifecycle and cross-process
    coherence as concerns; the upgrade path if history writes ever dominate a profile is a
    thread-local connection, and the Protocol does not change.

    **The write methods.** One transaction per method — do not batch steps into the run's
    transaction. A crash mid-run should leave the run row in its in-flight status with the steps
    written so far, which is the forensically useful state and is what per-method commits give for
    free; batching discards exactly the evidence you want afterwards. `finish_run` must raise when it
    updated zero rows: a silent no-op on an unknown run_id is a worse outcome than an exception.
    `metrics` and `attributes` are serialized with sorted keys so a stored blob is comparable.

    Write `tests/test_store.py` before the module, covering the `<behavior>` list.

    fragments to a list and appending the value to a parallel argument list — never by interpolating
    or formatting a value into the statement text. Table names and the sort direction cannot be bound
    parameters at all (both raise an operational error if you try), and this store has two tables and
    one sort direction, all known when the file is written, so they are literals in the string and
    never derived from caller input. A workflow id carrying a statement terminator and a drop must
    come back as an empty result with the table intact — that behaviour is what the test asserts, not
    the absence of a syntax pattern.

    **Clamp the limit.** A caller-supplied limit goes through a floor of 1 and a ceiling of 1000
    before it reaches the statement, so an absurd value cannot materialize the whole table and a zero
    or negative value cannot turn into a confusing empty result or a driver error.

    mode — measured as group- and world-readable on this host — and run history carries workflow ids,
    policy ids and metrics. Set owner-read/write-only on the database file right after creating it in
    `__init__`. Record in the module docstring that SQLite creates the `-wal` and `-shm` sidecars with

    document telling a user to copy "the store file" is wrong because there are three of them. The
    test asserts on every file matching the database name pattern in the directory, so it catches a
