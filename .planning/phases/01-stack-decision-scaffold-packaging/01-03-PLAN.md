    The `core` job runs on a `[ubuntu-latest, macos-latest]` OS matrix and executes four steps in this order: `uv lock --check` (the PACKAGE-03 drift gate — it exits non-zero when `pyproject.toml` and `uv.lock` disagree); `uv sync --locked --no-default-groups` (the core-only environment); a `uv run --no-sync --no-default-groups` Python assertion that `importlib.util.find_spec` returns `None` for each of `langgraph`, `crewai`, `ag2`, `langchain_core` and that `import eacp` succeeded, with a failure message naming PACKAGE-01 and both plausible causes (a framework added to `[project].dependencies`, or an extra leaking into it); and finally the test suite as a **separate step with its own `uv sync --locked`**, so the dev-group environment and the core-only environment can never be confused.

    Three flags in that job are load-bearing, not stylistic. `--no-default-groups`: without it `uv sync` installs the `dev` group by default, and once a later phase adds a framework to a dev or test group the assertion runs against an environment nobody ships — the job then never fails again (01-RESEARCH.md Pitfall 3). `--locked`: without it `uv sync` silently re-resolves and rewrites `uv.lock`, so the job stops proving reproducibility. And `find_spec` rather than `pip list | grep`: `find_spec` catches a framework reaching the environment by any route — vendored, transitive, or system-site-packages leakage — and does not execute the module.

    The `extra` job runs on a two-dimensional matrix: `os: [ubuntu-latest, macos-latest]` × `extra: [langgraph, crewai, ag2]`. It sets `fail-fast: false`, which matters: `crewai` publishes a nightly daily, and a CrewAI break must redden exactly one cell rather than cancelling the other five. Its steps are the `uname -m` arm64 guard (macOS only), `uv sync --locked --no-default-groups --extra ${{ matrix.extra }}`, then a probe passing the backend name through the `EACP_EXTRA` environment variable.

    That probe asserts two *independent* properties, and both are needed. First, that `import eacp` alone left `sys.modules` free of every framework root — even though the framework is now installed. Second, that `load_backend_module(backend)` returns the adapter module and can report its `FRAMEWORK_VERSION`. Neither implies the other: the `core` job proves a framework *is not installed*, while this job proves that when it *is* installed, `import eacp` still does not load it.

    The `uname -m` guard is three lines that convert a confusing upstream error into an explicit one. `macos-latest` resolves to macOS 26 arm64 today (verified), and that is exactly what D-05 wants — GitHub Actions' macOS runners are Apple Silicon, not the Intel host this project is developed on. But `-latest` labels float. If GitHub ever repoints it at x64, the `crewai` macOS cell would fail with an opaque `lancedb` wheel error that looks like a project bug and invites someone to "fix" it by deleting the extra. The guard emits a `::error::` naming `lancedb`, the absent x86_64 wheel and sdist, and the fix (pin an explicit arm64 runner label), then exits 1.
