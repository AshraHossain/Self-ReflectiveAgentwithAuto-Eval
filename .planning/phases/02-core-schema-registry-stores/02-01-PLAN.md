<objective>
Build the policy layer: the shared exception types, the capability vocabulary, a YAML loader that closes the three silent failure modes `yaml.safe_load` has, the strict `Policy` schema, and the canonical content hash.

Purpose: this is the phase's only trust boundary. Untrusted YAML bytes become a typed object here and nowhere else (02-RESEARCH.md §Architectural Responsibility Map). POLICY-04's content hash is what Phase 3's audit log and every Phase 5/6/7 run record pin themselves to — if the canonical form is unstable, the hash proves nothing and the governance claim collapses. 02-RESEARCH.md demonstrated two independent ways it goes unstable and one way a limit gets silently overridden before pydantic can see it; all three are closed here.

Output: `src/eacp/errors.py` (extended), `src/eacp/capabilities.py`, `src/eacp/policy.py`, `tests/conftest.py`, `tests/test_policy.py`.

Scope boundary: this plan does not enforce any policy (Phase 3), does not register anything (plan 02-03), and does not persist anything (plan 02-02). It produces a validated, content-addressed value object.
</objective>

    - `_StrictLoader`, a subclass of PyYAML's `SafeLoader`, with a mapping constructor that raises on

      result that is not a mapping. This is the single YAML entry point for the whole package; nothing
      else in `src/` may call into PyYAML.
    - `load_policy_file(path: str | Path) -> Policy` — reads the file, runs it through
      `load_yaml_mapping`, validates, and wraps every failure in `PolicyError`.

    Wrap PyYAML's own `ConstructorError`/`YAMLError` and pydantic's `ValidationError` in `PolicyError`
    so callers have one type to catch. When re-raising a validation failure, render the details with
    `errors(include_url=False)` — the default appends a documentation URL per error, which is noise in
    a CLI message. Include the policy file path in the message; per 02-RESEARCH.md §Pitfall 7 that is
    in scope, while interpreter or environment locations are not.

    The schema half — a frozen pydantic model with `extra="forbid"`, nine fields, no defaults on any
    of them:

    - `policy_id` and `version` are identity. Constrain `policy_id` to a conservative charset so it is
      safe in error messages, run records and (Phase 4) CLI output. `version` is a strict integer.
    - `max_tokens_per_run` is a strict integer with a floor of 1. Use the field-level strict type, NOT
      model-level strict configuration: 02-RESEARCH.md §Finding 2 measured that model-level strictness
      correctly blocks YAML `yes` but also rejects a plain YAML `100` for the cost field.
    - `max_cost_per_day` is a `Decimal` with a floor of 0, quantized by a field validator to a fixed
      exponent so `25` and `25.00` are the same value. Do not normalize instead of quantizing:
      `Decimal("100").normalize()` becomes `1E+2`, which serializes as the string `"1E+2"`.
      Lax `Decimal` already rejects booleans on its own — verified.
    - `allowed_tools`, `forbidden_tools`, `required_approval_nodes`, `compliance_tags` and `requires`
      are all `list[...]`, never an unordered collection type. A shared field validator rejects
      repeated entries and returns the list sorted. The ordering is what makes Task 3's hash
      independent of how the author wrote the file; the type choice is what makes it independent of
      which process serialized it (02-RESEARCH.md §Finding 1 measured three different orders from
      three runs of the same code).
    - `requires` is `list[Capability]`, so a typo is a load-time failure naming the field index
      rather than a gate that silently never matches.
