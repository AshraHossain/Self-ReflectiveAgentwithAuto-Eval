    Write `src/eacp/backends.py` verbatim from 01-RESEARCH.md §Pattern 2. The shape that matters:

    A module docstring stating that this module must not import any agent framework at module scope, that it stores adapter locations as strings, and that this is what keeps `import eacp` framework-free (PACKAGE-01) while still shipping three adapters (PACKAGE-02). Then `from __future__ import annotations`, `import importlib`, `from types import ModuleType`, and `from eacp.errors import MissingExtraError` — those four imports and nothing else. No framework import at any scope in this file.

    `_BACKENDS: dict[str, tuple[str, str, str]]` maps backend name to `(adapter module path, extra name, framework root module)` with exactly three entries: `"langgraph"` → `("eacp.adapters.langgraph_adapter", "langgraph", "langgraph")`, `"crewai"` → `("eacp.adapters.crewai_adapter", "crewai", "crewai")`, `"ag2"` → `("eacp.adapters.ag2_adapter", "ag2", "ag2")`. All plain strings — that is the whole trick.

    `available_backends() -> tuple[str, ...]` returns `tuple(_BACKENDS)`. `load_backend_module(backend: str) -> ModuleType` does three things in this order, and the order is load-bearing:

    1. Look `backend` up in `_BACKENDS` first, raising `ValueError` naming the unknown backend and the sorted known set on a miss (`raise ... from None`, so the `KeyError` does not clutter the traceback). This dict lookup *before* any `import_module` call is the phase's one ASVS V5 control: a caller-supplied string is never interpolated into an import. It is also the Phase 1 seed of Phase 2's entrypoint allowlist (WORKFLOW-02).
    2. `importlib.import_module(module_path)` — the only import site in the package.
    3. On `ModuleNotFoundError`, compare the root of `exc.name` against the known `framework_root` and **re-raise unchanged when they differ**, before translating anything into `MissingExtraError`. This one line is the difference between a good error and a lost afternoon: per 01-RESEARCH.md Pitfall 2, without it a typo'd internal import inside `crewai_adapter.py` in Phase 6 reports "Backend 'crewai' requires the 'crewai' package... pip install eacp[crewai]" while CrewAI is in fact installed. Verified working both ways in research: the absent-framework case produces `MissingExtraError`, and an adapter with a genuinely bad internal import propagates `ModuleNotFoundError: eacp.does_not_exist` untouched. The `MissingExtraError` message must contain the framework root name and the literal `pip install 'eacp[{extra}]'` command, and nothing else — no filesystem paths, no environment data.

    Write `src/eacp/adapters/__init__.py` as a docstring only, verbatim from 01-RESEARCH.md §Pattern 3: it states that importing this package must not import any agent framework, that adapter modules are loaded on demand by `eacp.backends.load_backend_module`, and that adding imports here breaks PACKAGE-01. Zero import statements. The docstring is not decoration — it is addressed to the Phase 5/6/7 author who will be thinking about ergonomics rather than this invariant.

    Write the three adapter placeholders, each roughly six lines and each following the identical shape from 01-RESEARCH.md §Pattern 3: a docstring naming the PyPI package and version range, the import root, and the `pip install 'eacp[X]'` command; `from __future__ import annotations`; a module-scope import of the framework (`import langgraph`, `import crewai`, `import ag2`) carrying a `# noqa: F401` comment noting that it proves the extra resolved and is lazy via `eacp.backends`; `BACKEND` set to the backend name; `FRAMEWORK_VERSION` set from `getattr(<framework>, "__version__", "unknown")`. Each docstring states that real adapter logic lands in its own later phase — LangGraph in Phase 5 (LANGGRAPH-01/02), CrewAI in Phase 6 (CREWAI-01/02/03), ag2 in Phase 7 (AG2-01/02).

    Module-scope framework imports here are correct and preferred, not an oversight. The adapter module *is* the lazy boundary — it is only ever reached through `load_backend_module`. A function-body import adds indirection for no gain, and a module-level `try: import crewai / except ImportError: pass` is actively worse: it yields a module that imports "successfully" in a half-initialised state, converting a clean install error into a confusing `AttributeError` later.

    The ag2 module is `ag2_adapter.py`. Never `autogen_adapter.py`, `pyautogen_adapter.py`, or `autogen_agentchat_adapter.py` — those are four different codebases (01-RESEARCH.md Pitfall 5). Its docstring does deliberately name `autogen`, `pyautogen`, and `autogen-agentchat` as what this adapter is *not*, which is the point of the docstring. Any `autogen` gate must therefore be scoped to filenames, backend keys, and `pyproject.toml` — never to raw text in `src/`. Do not "fix" that docstring to satisfy a text grep.

    Nothing else goes in these files. Per 01-RESEARCH.md Pitfall 7 the tell-tales that Phase 1 has grown a policy engine are: any `pydantic.BaseModel` subclass, any `typing.Protocol` (so no `Adapter` protocol and no `AdapterCapabilities` — both are Phase 2), any `yaml.safe_load`, any `sqlite3` import. If a framework *type* is ever needed in a signature, the pattern is `from __future__ import annotations` plus a `TYPE_CHECKING` block so annotations stay string-only and the type-only import never executes — but nothing in these placeholders has a signature yet, so add no `TYPE_CHECKING` block now.
